# 数据流与用户模型

> 一次查询从消息到出图的完整链路，以及 NoteUser / MysUser 两级用户模型与 CK 分配池。

## 请求链路（角色查询为例）

```
用户消息 "#刻晴"
  │
  ├─ role.js: accept() 拦截 → gsCfg.getRole(msg) 匹配角色别名
  │    设置 e.msg = "#角色详情", e.roleId = 10000042, e.roleName = "刻晴"
  │
  ├─ rule 匹配 "#角色详情" → roleDetail()
  │    │
  │    ├─ MysInfo.init(e, "detail")  ← 查询入口
  │    │    ├─ MysInfo.getUid(e) → NoteUser.create(e) → getUid(game)
  │    │    │   (消息携带 UID → 用户绑定 UID → 群名片 UID)
  │    │    └─ MysInfo.getCookie(e) → MysUser.getByQueryUid(uid)
  │    │         └─ DailyCache.zMinKey("query-detail")  ← 最少查询次数的 CK
  │    │
  │    ├─ new MysApi(uid, ck) → getData("detail", params)
  │    │    ├─ fetch() → 米游社 API（带 DS 签名、设备指纹）
  │    │    └─ 遇 10001+login → ckRefresh.tryRefreshCk：stoken 换新 cookie 重试
  │    │
  │    └─ MysInfo.checkCode(res) → 错误码处理（失效/上限/验证码等）
  │
  └─ 渲染: Common.render("genshin", "html/player/player", data)
       └─ 由 miao-plugin 的 puppeteer 渲染
```

## CK 分配算法（Redis Sorted Set）

`DailyCache` 实现了基于 Redis ZSet 的 CK 负载均衡：

1. 查询 `detail` 表的 `count` 子表 → `zRangeByScore(0, 60)` 获取所有可用 CK
2. 取 `score` 最小的 key（即查询次数最少的 CK） → `zMinKey()`
3. 查询成功后 `zAdd(detail, ltuid, uid)` → 更新计数
4. CK 失效时 `zDisableKey(detail, ltuid)` → score 设为 99（不再被分配）
5. 数据按日期分片（`MM-DD`），跨天自动过期清理

## 用户模型层级

```
NoteUser（QQ 维度）
  ├─ mysUsers: { [ltuid]: MysUser }   ← 一个 QQ 可绑定多个 CK
  ├─ _games: { gs: {uid, data}, sr: {...}, zzz: {...} }
  │    └─ data: { [uid]: {type: "ck"|"reg"} }  ← CK 自动生成的 uid 或手动注册的 uid
  │
  └─ MysUser（ltuid 维度）
       ├─ ck: string          ← 完整 Cookie 字符串
       ├─ type: "mys"|"hoyolab"
       ├─ uids: { gs: [...], sr: [...], zzz: [...] }
       └─ initCache()         ← 将 uids 加入 DailyCache 查询池
```
